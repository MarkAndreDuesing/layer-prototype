# Generate each scene object as its own free layer

For a first-draft storytelling game where every scene object is a separately prompted, individually regenerable layer, the best free stack today is **modular: generate each object on its own, then cut it out or emit it with native alpha, and composite in your own code**. Prompt-to-layers and image-to-layers models exist, but they decompose a *whole* scene, which works against per-object regeneration. Two routes produce transparent objects directly on a free 16 GB T4: **LayerDiffuse on SDXL/SD1.5** (Apache-2.0 code, OpenRAIL-M weights, fits a T4 comfortably) and **Qwen-Image-2.1**, which confirmed native text-to-RGBA output in a 7B model with GGUF quants, but under a **non-commercial Qwen Research License** ([HF](https://huggingface.co/Qwen/Qwen-Image-2.1)). For cut-outs, **BiRefNet (MIT)** or **BEN2 base (MIT)** are the commercially safe matting choices ([BiRefNet](https://huggingface.co/ZhengPeng7/BiRefNet), [BEN2](https://huggingface.co/PramaLLC/BEN2)). The best free place to run the generator is **Kaggle** (about 30 GPU hours a week, though that figure comes only from secondary sources). **Modal's $30/month credit** gives you a clean HTTP endpoint. Do not run a tunnelled web UI on free Colab: its FAQ explicitly bans this. Every VRAM fit and timing below is an **estimate from model sizes, not a tested run**.

## Per-object generation beats whole-scene decomposition for regenerable layers

The game's requirement settles the architecture before any model comparison. If each object (a lantern, a fox, a cottage) has its own prompt and must be re-rolled without touching the others, then the layer boundary has to exist *before* generation. Image-to-layers models such as **Qwen-Image-Layered** take one finished image and split it into RGBA layers ([HF card](https://huggingface.co/Qwen/Qwen-Image-Layered)). Regenerating a single object therefore means regenerating the whole scene and decomposing it again, and the layers will not stay stable from one run to the next. Joint prompt-to-layers research models (CLD, ART, OmniPSD) have the same coupling, and all of them are built on FLUX.1-dev. A per-object pipeline does better on every axis that matters for a prototype. It is cheaper per regeneration, each asset is stored and cached on its own, and you can swap the generator without touching the rest. The cost is lighting and perspective coherence, because objects generated in isolation do not share a light source. LayerDiffuse's SD1.5 "foreground conditioned on a given background" mode partly fixes this ([diffusers port](https://github.com/rootonchair/diffuser_layerdiffuse)). IC-Light SD1.5 (Apache-2.0) can relight a foreground against a background ([IC-Light](https://github.com/lllyasviel/IC-Light)).

## Resolving the earlier report's open claims

The earlier report left eight claims unverified. Here is where each one stands now.

**Qwen-Image-2.1 is real, and its RGBA output is confirmed.** The official card lists text-to-transparent generation, transparent layer editing and subject extraction from a 7B, 32-layer DiT. The licence is the **non-commercial Qwen Research License, not Apache**. The model tree shows 172 quantized builds ([HF](https://huggingface.co/Qwen/Qwen-Image-2.1)). unsloth's GGUF denoiser comes at **Q4_K_M 4.2 GB, Q8_0 7.64 GB and F16 14.2 GB**, and the Qwen3-VL-8B text encoder adds about 5 GB at Q4 ([unsloth](https://huggingface.co/unsloth/Qwen-Image-2.1-GGUF)). The release date is not on the card.

**FLUX 3 Image Klein exists**, announced on 15 October 2026. It is 5.6B parameters, 11.2 GB at BF16, under the FLUX Kommunity License, and **has no transparency or layer features** ([BFL blog](https://bfl.ai/blog/flux-3-image-klein)). The card's peak-memory figures of 25–31 GB make it a poor fit for a T4 ([HF](https://huggingface.co/black-forest-labs/flux-3-image-klein)).

**LayerDiffuse licences and the FLUX port.** The main LayerDiffuse code is Apache-2.0 and its weights are OpenRAIL-M ([repo](https://github.com/lllyasviel/LayerDiffuse), [HF](https://huggingface.co/LayerDiffusion/layerdiffusion-v1)). The ComfyUI nodes are Apache-2.0 and SD/SDXL-only ([ComfyUI-layerdiffuse](https://github.com/huchenlei/ComfyUI-layerdiffuse)). The FLUX port is released as a LoRA plus a TransparentVAE, but its repo has no licence file, and the FLUX.1-dev base licence makes it non-commercial ([FireRedTeam](https://github.com/FireRedTeam/LayerDiffuse-Flux)).

**Research model weights.** Only some of the research models have downloadable weights. CLD has MIT code and weights at thuteam/CLD ([GitHub](https://github.com/monkek123King/CLD)). LayerD has Apache-2.0 code ([GitHub](https://github.com/CyberAgentAILab/LayerD)). OmniPSD has code but no weights link ([GitHub](https://github.com/showlab/OmniPSD)). ART's HF repo returned **HTTP 401** when checked. DiffDecompose, PSDiffusion, RefLayer, LiWi, LASAGNA and LayerDecomp have **no released weights** ([DiffDecompose](https://github.com/Wangzt1121/DiffDecompose), [LiWi](https://arxiv.org/abs/2605.14552)).

**Qwen-Image-Layered.** It is Apache-2.0, about 20B parameters, and image-to-layers only. The card recommends 4 layers at 640 px ([HF](https://huggingface.co/Qwen/Qwen-Image-Layered)). Seven quantized repos exist, including unsloth GGUF, FP8, and SDNQ 4-bit and 8-bit builds ([quant listing](https://huggingface.co/models?other=base_model:quantized:Qwen/Qwen-Image-Layered)). A DataCamp attempt on a Colab T4 **ran out of system RAM** while downloading more than 57 GB of weights ([DataCamp](https://www.datacamp.com/sv/tutorial/qwen-image-layered)). A community claim that a 3.2 GB Q4 file exists is not credible for a 20B model, where Q4 should be about 11–12 GB. Hosted, it costs **$0.05 per image on fal.ai** ([fal](https://fal.ai/models/fal-ai/qwen-image-layered)). Replicate hosts it but showed no price ([Replicate](https://replicate.com/qwen/qwen-image-layered)).

**Matting licences.** BiRefNet, BEN2 base, InSPyReNet and Florence-2 are MIT. SAM 2.1 and LaMa are Apache-2.0. RMBG-2.0 is CC BY-NC. ObjectClear is under the non-commercial NTU S-Lab License ([ObjectClear](https://github.com/zjx0101/ObjectClear)). IC-Light v2 weights are unreleased and announced as non-commercial ([discussion](https://github.com/lllyasviel/IC-Light/discussions/98)). One trap: rembg's code is MIT, but its **default model, bria-rmbg, is non-commercial**, so select a BiRefNet model explicitly ([rembg](https://github.com/danielgatis/rembg)).

**Hosting ToS** is covered in the next section.

## Colab forbids the tunnel; Kaggle, ZeroGPU and Modal fill the gap

A prototype app that calls a remote ComfyUI or API is exactly what Colab's free tier prohibits. On all runtimes, the FAQ bans "web service offerings not related to interactive compute" and "connecting to remote proxies". On free runtimes it also bans "bypassing the notebook UI to interact primarily via a web UI", and those sessions can be terminated without warning ([Colab FAQ](https://research.google.com/colaboratory/faq.html)). Colab is fine for interactive work inside the notebook, such as batch-generating assets into Drive, but not as a backend.

**Kaggle** is the most practical free GPU notebook. Secondary sources report about **30 GPU hours a week** and about 12-hour sessions ([gpuperhour](https://gpuperhour.com/blog/free-cloud-gpus-and-credits)). A community repo runs ComfyUI on Kaggle through a Pinggy tunnel ([comfyui-kaggle](https://awesome.ecosyste.ms/projects/github.com%2Fkayas881%2Fcomfyui-kaggle)). Kaggle's own ToS and docs could not be read, so whether tunnels are permitted there is **unverified, not approved**.

**Hugging Face ZeroGPU** does not require PRO. A free account (verified email, older than 30 days) can host **2 Gradio Spaces on half of an RTX Pro 6000 (48 GB)**, but gets only **5 GPU-minutes per day** ([HF docs](https://huggingface.co/docs/hub/spaces-zerogpu)). That is enough for matting and segmentation calls through `gradio_client`, but not for a day of diffusion.

**Modal's Starter plan** gives **$30/month in credits**, which buys roughly 50 T4-hours at about $0.59 per hour before region multipliers. It provides a ToS-clean, stable HTTPS endpoint with weights cached in a Volume ([Modal pricing](https://modal.com/pricing)). **Lightning AI's** free plan is a further fallback: about 30 credits, which its FAQ says is roughly 50 interruptible GPU hours ([Lightning](https://lightning.ai/pricing)).

## Recommended first-draft stack and fallback

**Primary (commercial-safe and T4-friendly).** Generate each object with **LayerDiffuse SDXL** through the MIT diffusers port or the ComfyUI nodes, which gives native alpha with no matting step. For backgrounds, use plain SDXL, or FLUX.2 Klein 4B (Apache-2.0). Use LayerDiffuse SD1.5's fg-given-bg mode when an object needs to match its scene. Run it on Kaggle for batch asset generation, or on Modal when the game needs a live endpoint. Composite in the game engine using stored per-object prompts and seeds, so any single layer can be re-rolled.

**Quality alternative (non-commercial prototype only).** If LayerDiffuse quality falls short, use **Qwen-Image-2.1** GGUF (Q8 denoiser, Q4 encoder) for native text-to-RGBA objects. It is a stronger modern generator, but its licence must be swapped out before any commercial release.

**Fallback (any generator).** Generate each object on a flat background with FLUX.2 Klein 4B, Z-Image Turbo or SDXL. Then cut it out with **BiRefNet or BEN2 base**, which run on CPU or ZeroGPU. When an object has to be pulled out of an existing scene, use **Florence-2 + SAM 2.1** to segment it and **LaMa** to fill the hole. Keep Qwen-Image-Layered (fal.ai at $0.05 per image) for occasional "decompose this finished illustration" jobs, not for the core loop.

## What remains genuinely unverifiable

None of the T4 VRAM fits or speeds in this report are tested runs. No project publishes T4 memory or timing figures, so every fit is arithmetic on file sizes, and actual peaks depend on resolution, offload and the T4's lack of bf16. Kaggle's quota and tunnel policy rest on secondary sources because its official pages render only with JavaScript. ART's weight status (401), the PrismLayers/ART+ licence, the OmniPSD licence text, the SAM 3 licence text and OmniEraser's licence (none stated, so treat it as all rights reserved) are all still open. No maintained public Kaggle or Colab notebook was found for LayerDiffuse, Qwen-Image-2.1 or Qwen-Image-Layered. No transparency adapter was found for Z-Image Turbo or FLUX.2 Klein, but Civitai was not searched directly.

## Conclusion

The thing that decides this is not model quality. It is where the layer boundary sits. The newest layer models, Qwen-Image-Layered and the FLUX-based research decomposers, solve "split a finished picture", which is the wrong problem for a game that re-rolls objects one at a time, and they are also the hardest to fit on free hardware. Native-alpha generation per object, built on an older but well-supported base such as SDXL with LayerDiffuse, is the cheapest, licence-clean path. Once the per-object pipeline exists, the generator becomes a replaceable component: Qwen-Image-2.1 now, or a commercially licensed RGBA model later, with no change to the game's data model.
